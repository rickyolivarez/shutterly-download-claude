# CLAUDE.md — guidance for AI assistants working in this repo

This file is loaded automatically when Claude Code (or another agent) opens this repository. It is **the recommended entry point** for users who clone this repo and want an AI to walk them through the process from scratch.

If you are a human reading this: this is also a valid runbook. Skip the agent framing and treat it as a step-by-step guide.

---

## What this repo does, in one paragraph

This is an unofficial bulk archival tool for Shutterfly photo libraries. It does two things: (1) walks the user's entire Shutterfly library via the same internal API the web SPA uses and downloads every photo/video at the quality Shutterfly's "Download" button delivers, and (2) for videos specifically, triggers an AWS Glacier restore and retrieves the **true original** file (typically 10-150× larger than the medium tier). The pipeline is resumable, throttled to avoid rate limits, and survives multi-day runs.

## Recommended walkthrough for a brand-new user

If a user has just cloned this repo and wants to actually use it, walk them through the steps below **in order**. Do not skip ahead. Each step gates on the previous one.

### Step 0 — Read `docs/SETUP.md` and sanity-check the environment

**Always start here.** Have the user open `docs/SETUP.md`. It covers:

- **Dependency requirements** (Node 18+, ExifTool, Playwright, PowerShell on Windows)
- **Assumptions** the project makes about their environment (has a Shutterfly account, can do an interactive login, machine stays awake for days, etc.)
- **Known issues** (Windows session-kill, photo originals not retrievable, ~3% Glacier slow-tail, etc.)

After they've skimmed `SETUP.md`, confirm with the user:

1. **Operating system.** Windows, macOS, or Linux. Most testing has been done on Windows.
2. **Do they have a Shutterfly account with photos in it?** Required.
3. **Do they have enough disk space?** Rough estimate: ~3 GB per 1,000 medium-quality items, plus 5-150× more if they plan to upgrade videos. For a typical Shutterfly account this is 50-200 GB without upgrade, 200 GB to 1.5 TB with upgrade.
4. **What's the goal?** Three common modes:
   - "Archive everything to local disk" → Phase 1 only (downloader.js)
   - "Archive + push to cloud" → Phase 1 + Drive for Desktop sync (NOT Google Photos directly — see `docs/CLOUD_SYNC.md`)
   - "Archive at maximum quality" → Phase 1 + Phase 2 (upgrade.js)
5. **Will the machine stay awake for days?** Bulk download takes 1-3 days; video upgrade takes another 5-7 hours. The machine must NOT sleep. If on Windows: disable auto-update during Active Hours OR plan to use `scripts/launch_durable.ps1`.

Tell the user which mode they're in and what total time/storage to expect.

### Step 1 — Install dependencies

```bash
git clone <this-repo-url>
cd <repo-dir>
npm install
npx playwright install chromium
```

For ExifTool:
- **Windows**: download from [exiftool.org](https://exiftool.org/), unzip, rename `exiftool(-k).exe` → `exiftool.exe`, place in your PATH
- **macOS**: `brew install exiftool`
- **Linux (Debian/Ubuntu)**: `sudo apt install libimage-exiftool-perl`

Verify: `node --version` (should be 18+) and `exiftool -ver` should both work.

### Step 2 — Configure credentials

```bash
cp .env.example .env.local
```

Edit `.env.local`:
```
SHUTTERFLY_EMAIL=your.email@example.com
SHUTTERFLY_PASSWORD=your-password
```

**Remind the user**: `.env.local` is in `.gitignore` — never commit credentials.

### Step 3 — One-time interactive login

```bash
node manual_login.js
```

This opens a Playwright browser window pointed at Shutterfly's login page. **The user completes the login by hand**, including any 2FA challenge. The script waits up to 15 minutes. When the URL changes to `/library`, the script saves session cookies to `auth.json` and closes.

If they hit issues:
- "Browser opens then closes" → delete `auth.json` (if present) and retry `node manual_login.js`
- "2FA didn't complete in time" → just re-run; you have another 15 minutes
- "Suspicious activity" warning from Shutterfly → log in via [shutterfly.com](https://shutterfly.com) first, complete any verification, then re-run `manual_login.js`

See `docs/TROUBLESHOOTING.md` for full coverage.

### Step 4 — Bulk download (Phase 1)

```bash
node downloader.js --count 50000 --out ./downloads --rate-ms 5000
```

What this does:
1. Sniffs JWT + X-API-Key from a headless browser session
2. Walks the library newest-to-oldest via `getPaginatedMoments`
3. Downloads each item to `./downloads/` with a date-prefixed filename
4. Appends each item's metadata to `./downloads/manifest.json` (atomic writes)
5. Logs errors to `./downloads/errors.log` — does NOT stop the run on failures

**Expected wall-clock**: about 1-3 days for 30,000-50,000 items at the default 5s rate. The script is designed to run unattended for that long.

**Monitor with**: in a second PowerShell window, run `powershell -ExecutionPolicy Bypass -File scripts/status.ps1`. It tails `downloads/manifest.json` + `downloads/errors.log` and shows live progress and ETA.

**Resume**: if it crashes or you kill it, run with `--resume` and it picks up from the last manifest entry.

### Step 5 — Decide whether to upgrade videos

Before running upgrade.js, run an inventory check. The manifest is JSON — query it with a one-liner:

```bash
node -e "const m=require('./downloads/manifest.json');const v=Object.values(m.entries).filter(e=>e.type==='video'&&e.orig_filesize);const r=v.map(e=>e.orig_filesize/e.bytes).sort((a,b)=>b-a);console.log('videos:',v.length,'median ratio:',r[Math.floor(r.length/2)]?.toFixed(1)+'x','top 5:',r.slice(0,5).map(x=>x.toFixed(1)+'x').join(','))"
```

This prints the count of video entries, the median `orig_filesize / bytes` ratio, and the top 5 ratios. If the median is close to 1.0, originals don't add much. If many are 5-150× larger (typical), upgrade is worth it.

**Storage budget check**: roughly 10× the video portion of your current `./downloads/` size. If you don't have that much disk space, stop here.

### Step 6 — Test the upgrade pipeline on a few UIDs first

```bash
node upgrade.js --limit 10 --commit --watch --skip-status-check
```

This selects the 10 videos with the BEST upgrade ratio, runs the full pipeline end-to-end, and commits the changes. It will take 3-5 hours (Glacier thaw latency) even for just 10 files — that's normal.

After it completes, verify:
- File sizes in `./downloads/` for those 10 UIDs increased dramatically
- `./downloads/manifest.json` shows `quality: "original"` for those entries
- `./downloads/video_upgrades.jsonl` records 10 `committed` events with no `verification_failed`

If all 10 worked, proceed to the bulk run. If many failed verification, read `docs/TROUBLESHOOTING.md` before continuing.

### Step 7 — Bulk upgrade the full library

There are two viable patterns. Pick based on what suits the user's schedule.

#### Pattern A — Run-it-all (simplest, ~5-7 hours unattended)

```bash
node upgrade.js --limit 5000 --commit --watch --skip-status-check
```

Or on Windows, for crash-resistant launch:

```powershell
# In an elevated PowerShell window:
scripts\launch_durable.ps1 -Script upgrade.js -ScriptArgs "--limit 5000 --commit --watch --skip-status-check"
```

Phase 2 (unfreeze, 13 min) → Phase 3 (Glacier wait, 3-5h) → Phase 4 (download, 1-2h) → done. Walk away.

#### Pattern B — Split for human convenience (RECOMMENDED if you can't leave it overnight in one go)

The `--unfreeze-only` flag lets you split the work cleanly:

```bash
# Evening — run JUST the unfreeze step (takes ~13 min, then exits)
node upgrade.js --limit 5000 --commit --unfreeze-only --skip-status-check

# Sleep (Glacier thaws overnight, free — no machine activity required)

# Morning — run the download phase
# All videos are already thawed, so this is FAST (~1-2 hours)
node upgrade.js --limit 5000 --commit --watch --skip-status-check --max-wait 240
```

**Why this is better when you have control over the schedule:**
- Evening unfreeze: 13 minutes hands-on, then your machine can sleep
- Glacier does its 3-5h restore work on AWS's side overnight (your machine doesn't need to be awake)
- Morning download: 1-2h instead of 5-7h, because the wait already happened
- Glacier retention is 24h after restore completes, so you have all day to come back to it

**Expected wall-clock** for either pattern: 5-7 hours of TOTAL upgrade time. Pattern A is one continuous block; Pattern B splits it across calendar days with maximum hands-off time. See `docs/MEDIA_UPGRADE.md` for the phase-by-phase breakdown.

**Monitor with**: double-click `scripts\upgrade_status.cmd` (Windows). The dashboard auto-detects the running process, shows progress across multiple runs if you've restarted, and works even after the run completes.

#### Pattern C — Cleanup after a stalled run (`scan_and_grab.js`)

If a long upgrade.js run gets stuck on the Glacier slow tail (no new commits for 1-2 hours, `thawing` count not decreasing), do NOT just keep waiting. The script `scan_and_grab.js` does a one-shot probe of every pending UID and grabs anything currently thawed:

```bash
# Kill the stalled upgrade.js first
# Then run the cleanup pass:
node scan_and_grab.js --commit
```

What it does (in ~5-15 min for a typical leftover):
- Probes each pending UID via `moment.downloadDetails`
- Downloads any that return HTTP 206 (thawed)
- Skips ones that return HTTP 403 (still cold)
- Exits cleanly with a summary

This is the cleanup recipe we discovered in production: a stalled run often has dozens of UIDs that ARE thawed but the producer just hasn't gotten back around to them yet. `scan_and_grab` catches those quickly. Cold UIDs that need fresh Glacier restore should then be handled with `upgrade.js --unfreeze-only` (Pattern B from above).

#### What's realistic — set expectations

For a 4,000-5,000-video library, a complete campaign typically takes **1-3 days of intermittent attention**, NOT one continuous 5-7h session. Expect:
- Windows Updates or sessions kill runs → use `scripts/launch_durable.ps1`
- ~5% of UIDs are in Glacier's slow tail (6-12+ hours) → max-wait timeout is normal
- Multiple runs needed (Run 2, 3, 4 with rotated logs is the production reality)
- Final ~5% may need `--unfreeze-only` overnight + cleanup the next day

A library will end at **~94-95% upgraded** if you're patient. Going to 100% requires either an overnight `--unfreeze-only` cycle for the remaining UIDs, or accepting the few permanent verification failures.

### Step 8 — Handling interruptions

If the process dies mid-run (Windows Update, RDP disconnect, OS crash, etc.):

1. Rotate the logs:
   ```powershell
   Move-Item .\downloads\upgrade.log .\downloads\upgrade.log.run1.bak
   Move-Item .\downloads\upgrade.err .\downloads\upgrade.err.run1.bak
   ```
2. Re-launch with the same command. The manifest's `quality: 'original'` field tells `upgrade.js` to skip already-committed UIDs.
3. AWS Glacier keeps thawed objects warm for 24 hours, so a restart within that window picks up where it left off with minimal re-thaw cost.

Full procedure: `docs/TROUBLESHOOTING.md` § "Process killed mid-run."

### Step 9 — Push to the cloud (OPTIONAL)

Cloud sync is **entirely optional**. The tool works perfectly standalone. Skip this step unless the user wants a cloud backup.

If they do want cloud:

- **Recommended: Google Drive via "Drive for Desktop"** pointing at the local `./downloads/` folder. Replace-in-place works correctly — `upgrade.js`'s file swaps are pushed as new revisions with the file ID and shareable link preserved. ✓
- **Strongly NOT recommended: Google Photos backup directly on the folder.** Google Photos is append-only — when `upgrade.js` swaps a medium video for an original, Photos uploads it as a SECOND library item, leaving the old one too. You'll get thousands of duplicates. If the user wants their content visible in Google Photos at original quality, the path is: sync to Drive first, then optionally separately upload chosen files to Photos.
- **Dropbox / OneDrive / iCloud Drive**: not formally tested but expected to behave like Drive (replace-in-place works).
- **iCloud Photos**: similar duplication problem as Google Photos. Avoid.

Verify the user has enough cloud quota BEFORE pushing originals. A typical upgraded library is ~400 GB to 1.3 TB. Google One 2 TB plan covers most personal cases.

Full details: [`docs/CLOUD_SYNC.md`](docs/CLOUD_SYNC.md).

#### After Drive sync starts: handling "files too small" errors

If the user has Drive for Desktop syncing `downloads/`, Drive's tray icon will show a "Some files are too small" error for ~30-100 of the Shutterfly compressed-display JPGs. Google Photos rejects any image whose short edge is under 256 px, and Shutterfly's compressed tier is typically 150-300 px on the long edge.

Run `scripts\upscale_too_small.ps1`:

```powershell
# 1. Find the rejected files by parsing Drive's local logs
.\scripts\upscale_too_small.ps1 -Mode discover

# 2. Dry run (writes upscaled copies to downloads\.upscale_staging\ — does not touch originals)
.\scripts\upscale_too_small.ps1 -Mode fix

# 3. Replace in place (backs originals up to downloads\.upscale_backups\)
.\scripts\upscale_too_small.ps1 -Mode fix -Commit
```

Default settings: width 1000 px (aspect preserved), Lanczos resampling, JPEG quality 90, EXIF preserved via ExifTool, `DateTimeOriginal` derived from filename when the original JPG has no date tag. Drive auto-retries on its next scan; no UI action needed.

The second Drive error class — "exceeds the daily upload limit for Google Photos" — is a per-account quota (~75 GB/day). Drive auto-retries the next day. No action needed.

See `docs/TROUBLESHOOTING.md` § "Google Drive / Google Photos sync errors" for full coverage.

## Common pitfalls to warn the user about

- **"Photos can be upgraded too, right?"** No. Shutterfly does not expose any higher-quality photo path. Only videos have the Glacier-original pipeline. CCPA requests historically don't include original-quality photos either.
- **Running both downloader.js and upgrade.js simultaneously**: don't. They both write to `./downloads/manifest.json` and can race. Run them sequentially.
- **Killing the process with Ctrl-C during a commit**: usually safe (the commit step uses atomic rename), but the manifest may not reflect the last 1-25 commits since the last checkpoint. Restarting picks them back up.
- **"I want to test without actually changing my files"**: omit `--commit`. The script downloads to `./test/upgrade_test/` and only verifies, doesn't swap.
- **Running on a Windows server with auto-updates enabled**: the OS may restart and kill the process at 3 AM. Either disable auto-update during active hours or use `scripts/launch_durable.ps1`.

## Code conventions (if the user asks you to modify the code)

- Node.js, no TypeScript, no transpilation step. Edit `.js` files directly.
- No external dependencies beyond `playwright`. Don't introduce more without strong justification — this repo's value is in being easy to inspect and audit.
- All file writes that matter use the `tmp + rename` atomic pattern (see `renameWithRetry()` in upgrade.js and the manifest writes in downloader.js).
- The Shutterfly API endpoints are not stable. If something stops working, the first hypothesis should be "Shutterfly changed something" and the fix is to re-do the reconnaissance in `research/playwright/` (not committed to this repo, but documented in `docs/UID_DISCOVERY.md` and `docs/MEDIA_UPGRADE.md`).
- The `research/playwright/d1-d10` experiment scripts are NOT in the public repo — they contained sensitive auth state. The relevant findings are summarized in the docs.

## What the AI should NOT do without confirmation

- Run `manual_login.js` — requires the user to interact with the browser.
- Run `node upgrade.js --commit` — modifies the user's library. Always confirm scope first.
- Touch `auth.json`, `.env.local`, or any contents of `downloads/` — these are the user's data.
- Push to GitHub or open PRs — confirm with the user before any git remote operations.
- Suggest the user disable security features (Defender, antivirus) — instead, work around them (e.g., add the repo folder to Defender's exclusion list).

When in doubt, ask the user. Especially on the "this will modify your library" steps (Step 7).
